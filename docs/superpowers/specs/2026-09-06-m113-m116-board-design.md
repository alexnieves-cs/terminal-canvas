## 1. What Act I is for

Work items exist as panels (M19 Jira, M88 GitHub), teammates exist (M100), worktrees exist
(M37), edges exist (M78), review across worktrees exists (M86), the broker can write with a
spend card (M87, M102) — and no surface says "this item is being worked by that agent in
that lane, and its PR is here". On a canvas the card sits beside the lane's chat with the
edge between them meaning *dispatched*, and the review panel is one flight away. This is the
headline of 3.0.

**The shape.** A work item is a RECORD on the workspace beside groups, runs, bookmarks and
annotations, with the record rules: absent is every pre-M113 file; a malformed entry is
dropped by name and the list kept; `WORK_ITEMS_MAX` newest by `updatedAt`. Its state is four
words as DATA, never a string from a provider: `todo | working | review | done`. `working`
and `review` are set by the RUNTIME from events (a dispatch's first turn, a PR opened), never
by a drag between columns — a card you can drag to "done" is a board that lies. `todo` and
`done` are the user's. The provider's own state rides beside as `remoteState`, display only.

## 2. M113 — the record and its doors

### 2.1 `shared/work-items.ts`

```ts
export type WorkItemState = 'todo' | 'working' | 'review' | 'done'
export const WORK_ITEM_STATES: readonly WorkItemState[] = ['todo', 'working', 'review', 'done']
/** The states a USER may set. The runtime sets the other two; a drop target exists for these only. */
export const USER_SET_STATES: readonly WorkItemState[] = ['todo', 'done']
export const WORK_ITEMS_MAX = 200

export interface PersistedWorkItem {
  id: string
  source: 'github' | 'jira' | 'typed'
  /** `owner/repo#N`, `PROJ-12`; absent for typed. The IDENTITY for the dedupe. */
  key?: string
  title: string
  /** Absent for typed. */
  url?: string
  /** The opening context a dispatch sends; absent when the provider gave none. */
  description?: string
  state: WorkItemState
  /** The provider's own word, display only. */
  remoteState?: string
  teammateId?: string
  /** The lane's chat. Absent until dispatched. */
  panelId?: string
  worktreeId?: string
  pr?: { number: number; url: string }
  /** M114. Set when the lane chat was closed; the state stays. Cleared by a new dispatch. */
  note?: string
  createdAt: number
  updatedAt: number
}
```

- `parseWorkItems(raw, warnings)`: absent → `[]` with no warning; not an array → replaced,
  one warning; an entry missing `id`/`title`/`state`/`createdAt`/`updatedAt`, a `source`
  outside the three, a `state` outside the four, a `pr` without a numeric `number` and a
  string `url` → that entry dropped BY NAME, the list kept; a `key` on a typed item is kept
  (harmless); sorted newest `updatedAt` first, `WORK_ITEMS_MAX` kept.
- `carryWorkItem(item)`: the by-name rebuild every copy site spreads — every optional field
  written only when present. `verify:layout work.3` builds an item with every optional absent,
  carries it, and asserts `Object.keys` are exactly the required six.
- `upsertWorkItem(list, incoming, now)`: the dedupe. Identity is `key` when present (source
  + key), else `id`. A match UPDATES `title`, `url`, `description`, `remoteState` and
  `updatedAt` and keeps `state`, `teammateId`, `panelId`, `worktreeId`, `pr`, `note` — adding
  twice never duplicates and never resets a working item.
- `workItemRefusal`: `title` empty → `a work item needs a title`.
- Pure; no DOM, no React, no electron. `verify:layout work.1–.3`.

### 2.2 Where it lives

`PersistedWorkspace.workItems?: PersistedWorkItem[]` beside `annotations` — **absent on
disk when empty** (the store deletes the key, M93's rule), so a pre-M113 file never grows one.
`layout-schema.ts` appends `parseWorkItems` at the workspace parse; `layout-store.ts` writes
through the same coalesced atomic path. The renderer's `Canvas.tsx` holds the list in the
workspace state the way it holds `annotations`; mutations go through ONE history entry each.

### 2.3 The three doors

1. **`Add to board` on a GitHub or Jira work panel's row** (`GithubNode.tsx`, `JiraNode.tsx`):
   a `pf__verb` beside `Start session`, `data-work-add`. Builds the item from the row's
   `WorkItem`: `source` from the panel kind, `key` from the item (GitHub's `owner/repo#N` is
   the client's id already; Jira's is the issue key), `title`, `url`, `description`,
   `remoteState: item.state ?? undefined`. Goes through `upsertWorkItem`. The verb reads
   `Added` for two seconds on success (a `useState`, never a store) and `On board` when the
   key is already there. Adding twice updates, never duplicates — `verify:layout work.2`.
2. **`New work item…` in the palette** (`canvas` section, never `panel`): a text mode whose
   Enter mints a `typed` item with the title; empty refused with `workItemRefusal`.
3. **`tc board add <title>` at the control socket** — READ-WRITE, so refused at the URL door
   like M81's `status` (`a URL can only open`). Main does NOT write the store itself: the
   renderer OWNS the workspace it is rendering and would overwrite a main-side write on its
   next coalesced save. So `tc board add` goes the way `canvas:model` does — main asks the
   RENDERER over an ephemeral reply channel
   (`board:add` main→renderer with `board:add:reply:<stamp>`), the renderer upserts through
   the ordinary history path and replies with the id; a window that does not answer in 2 s
   yields `{ kind: 'error', error: 'no canvas is open to add to' }`. `tc board done <id>`
   (M115) rides the same channel with `op: 'done'`. `verify:control board.1`.

`board:add` is a main→renderer event and is added to BOTH IPC diagrams. It is not an invoke,
so `verify:ipc`'s count does not move for it.

### 2.4 Checks

- `verify:layout work.1` record rules: absent, not-an-array, each malformed arm by name, the
  cap, the sort.
- `verify:layout work.2` `upsertWorkItem`: a second add by key updates and keeps state; a
  typed item with the same title is a second item.
- `verify:layout work.3` `carryWorkItem`: every absent optional stays absent; every present
  one is carried.
- `verify:control board.1`: `tc board add` parses to `{ verb: 'board', op: 'add', title }`,
  an empty title refused, the URL door refuses `board`, the handler's reply arms (ok /
  no-window).

## 3. M114 — dispatch, the one verb

### 3.1 `dispatch(item, teammate)`

The renderer's `usePaletteActions` gains ONE member, `dispatchWorkItem(itemId, teammateId,
placeOverride?)`. The sequence, each step refusing by name and leaving the record untouched
when it does:

1. **The repository.** For a `github` item the repository is derived from `key`
   (`owner/repo`); the place chosen is the teammate's first place whose tree contains a
   clone of it — decided in MAIN by a new invoke `board:lane` (below), because only main
   can read `git remote get-url origin` under each place. For a `jira` or `typed` item
   there is no repository: the sheet lists the teammate's places and asks which (a single
   place needs no ask). No place → refused: `<name> has no place that holds <owner/repo> —
   add one in the Teammates pane` (M100's sentence shape).
2. **The lane.** `board:lane` (invoke, main): `{ itemId, teammateId, root }` → main runs the
   Places gate on `root` FIRST (M100's rule: the gate BEFORE `resolveCwd`), then
   `worktreeManager.ensureForPanel(chatPanelId, root)` with a chat panel id the renderer
   minted, returning `{ kind: 'lane', path, worktreeId, branch }` or the manager's `refused`
   arm verbatim. **The lane lives under `userData/worktrees`, outside every Place.** The
   Places gate therefore judges a worktree by its RECORD's `root`: `createPlacesGate` gains
   an optional `worktreeRootOf(path)` dep (main hands it the worktree records), and
   `check` asks `insidePlace` on the root when the path is a known lane. This is the
   one rule M114 adds to the gate, and `verify:teammates dispatch.1` pins both arms: a lane
   whose root is inside a place passes; a lane whose root is not is refused with the root
   named, never the lane path.
3. **The chat.** `agent:create` through the ordinary door with `cwd: path`, `teammateId`,
   and `appendSystemPrompt: DISPATCH_PROMPT` — the M81/M101 shape: a sentence saying what a
   dispatched item is, that the branch is the lane's, and that the work ends with the changes
   committed on that branch, never pushed and never merged (the return path is the user's
   `Open PR`). `ChatSource.dispatch?: true` is what a relaunch reads so the prompt rides
   every spawn (M81's rule: the CLI keeps no record of it). `carryBackend`'s sibling
   `carryChatMarks` carries it through both copy sites.
4. **The first message.** Title, key, url and description under a fixed header, sent through
   `agentSession.send` (which spawns). The record gets `teammateId`, `panelId`, `worktreeId`
   and `updatedAt`; state stays `todo` until the runtime says otherwise.
5. **The edge.** A plain M78 edge card → chat with the label word `dispatched`; **no
   trigger** — `handoffFires` and `HANDOFF_TRIGGERS` unchanged (a check that the table's five
   triggers are still five and that the edge's automation is absent).
6. **State → `working`** from the chat's first `turn-start` on that panel id, observed in the
   chat store's turn listener (the same hook `onChatTurnEnd` uses), never from the click.

### 3.2 The doors

- **Drag a card onto a teammate row** in the Teammates pane (`TeammatesPane.tsx`): the row
  is a drop target for `application/x-tc-work-item` only; the drop calls the verb.
- **`Assign to…`** on the card (M116's kind): a menu listing teammates, each disabled by
  name — no place covers this repository; the backend binary is absent (the teammate's
  chats need a CLI). The prompt's third reason, "no `chats` permission", names a permission
  the teammate record does not have (`chats` is its list of chat panel ids), so it is
  dropped and recorded under §8.
- **`Dispatch…`** in the palette, `canvas` section: picks the focused or selected card,
  then the same teammate list.

### 3.3 A card follows its lane

The card panel is PANEL-ANCHORED like an M93 annotation: the card record carries
`anchor?: { panelId, dx, dy }`, set at dispatch to sit at the chat's left, and `Canvas.tsx`
re-derives the card's rect from the chat's on every render the way `annotationPoint` does. A
drag of the card itself clears the anchor (the user chose a place). When the chat is closed
the card stays where it was (the anchor is pruned like `pruneAnnotations`), the record's
`panelId` is kept, state stays `working`, and `note: 'lane closed'` is set — never silently
back to `todo`. A new dispatch clears `note`.

### 3.4 Checks

- `verify:panels dispatch.1`: seed a `github` item and a teammate with a place holding a
  fixture repository; dispatch through the harness's fake runner; assert the lane's chat
  exists with `data-chat-backend`, the record's `panelId`/`worktreeId`, the edge with label
  `dispatched` and no automation, `working` after the fake runner's first turn-start, and
  the note after the chat is closed.
- `verify:teammates dispatch.1`: the gate's lane rule, both arms.
- `verify:viewport` gains nothing; `verify:groups` gains nothing.

## 4. M115 — the return path

### 4.1 Ahead of the root

On the lane chat's turn end, the card asks `git:status`... which reports ahead/behind of the
UPSTREAM. A lane's branch has no upstream until pushed. So M115 adds `buildAheadOfArgs(path,
base)` (`rev-list --left-right --count <base>...HEAD`) to `git-args.ts` and a `laneStatus`
arm to the review engine, base being the root's HEAD branch, and a `board:lane-status`
invoke returning `{ ahead, behind } | { kind: 'failed', reason }`. NO FETCH — `verify:review
git.1`'s text assertion still holds, and the card says `ahead of <root branch> by N` beside
it.

### 4.2 `Open PR`

Disabled by name when ahead is 0 (`nothing to open a PR for — the lane has no commits
past <branch>`), when GitHub is not connected (`notConnectedReason('github')`), when the
teammate lacks the `github` service (`<name> may not spend github — grant it in the
Teammates pane`), when the item has no `owner/repo` (`a PR needs a GitHub repository — this
item is <source>`), or when the lane is gone.

The verb does two outward things and both sit behind M102's spend card, asked ONCE on the
teammate's chat with branch, base and title in the card's text:

1. **`git push -u origin <branch>`** in the lane, run by main through the injected
   `GitRunner` with the user's own git credentials (the app holds none for git and passes
   nothing — the same as `worktree add`). Its failure arm is git's own `reasonLine`.
2. **`POST /repos/{owner}/{repo}/pulls`** through the broker — `main/github-client.ts`'s
   `openPullRequest` builds `{ title, head: branch, base, body }` and NEVER reads the
   credential store (three readers stay three); the audit row names the teammate. Failure
   arms in the credential rows' words (`rejected`, `unavailable`, `malformed`, `refused`),
   plus GitHub's 422 `A pull request already exists` mapped to an `exists` arm that reads the
   existing PR back with one GET so the card gets its `pr` anyway.

On success the record gets `pr: { number, url }` and state → `review`. `Review` on the card
opens M86's across-worktrees review panel (`across: true`) and flies to the lane's section
(the section keyed by `worktreeId`; the review node gains a `focusWorktreeId?` on its
subject, absent means the top).

### 4.3 `done`

The user's: the card's verb, the Board pane's `done` column drop, or `tc board done <id>`.
On a GitHub item with a `pr`, the sheet offers `Comment the PR on the issue` — a second
broker write (`POST /repos/{owner}/{repo}/issues/{n}/comments`) behind a second spend card;
declining it still marks done. Jira items: `review` writes nothing; `done` offers M24's
transition list through the existing `jira:transitions` / `jira:transition`. No new Jira
write.

### 4.4 Checks

- `verify:github pr.1`: `openPullRequest` over the fake broker — the POST's path and body;
  the four failure arms in the credential rows' words; the `exists` arm's GET; the comment
  door's path.
- `verify:review lane.1`: `buildAheadOfArgs` argv, `parseAheadOf`, the engine's failed arm;
  and `git.1`'s no-fetch text assertion re-run over the new function.
- `verify:layout work.4`: a `pr` field carried, and a `pr` with a non-numeric number dropped
  by name.

## 5. M116 — the Board pane, and the card in the world

### 5.1 The pane

`NavigatorPane` gains `'board'`; `Dock.tsx` gains the entry; `Navigator.tsx` renders
`BoardPane.tsx`: four columns over the same records, rows sorted by `updatedAt` desc, each
row naming the title, the key, the teammate's name and the lane (the chat's rail label), a

## 9. What green will not prove

`git push` from a lane reaches the remote with the user's credentials; that the POST opens a
real PR; that the comment lands on the issue. `npm run verify` reaches no network; the
suites drive a fake broker and a fake `GitRunner`.

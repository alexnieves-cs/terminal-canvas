# M199 — The run's own truth

## Problem and state table

The persisted run can say only that an entry exists and whether it has an outcome string.
`run-outcome.ts` therefore paints a mapped entry as `working` even when its live chat is queued
for the concurrency ceiling or asking a permission question. It also maps `a turn` to the generic
word `finished`, which blurs an execution result into task completion.

The projection separates five axes:

| Axis | Values | Authority |
|---|---|---|
| Execution | not run, queued, running, ended, unknown | immutable run entry plus live session |
| Queue reason | upstream, current turn, concurrency ceiling | run mapping plus session snapshot |
| Blocker | pending approval, terminal keyboard, budget/refusal note | main-owned approval/session facts mirrored in renderer |
| Execution result | turn complete, exit 0, failed, skipped, stopped, no outcome | run entry outcome |
| Task disposition | todo, working, review, done | work-item record, outside the run projection |

Priority is pending approval, then an explicit session queue, then the immutable run record.
An approval carries its actual tool and argument while live. A terminal `wants-you` state carries
only the honest keyboard instruction because there is no structured question to invent.

## Persistence and races

The projection is pure. It does not write a request id, grant, or pending question into the run.
That keeps an answered or abandoned approval from becoming actionable after reload. Once main
answers or drops the request, the live overlay disappears and the immutable run entry is shown.
If a run is sealed with an entry that has no outcome, the result is `no outcome`, never working.
If a mapping is missing, the node is `not run`; if the mapping exists but no entry does, it is
queued behind upstream work.

## Backend differences

A structured approval is answerable only when the live mirror supplies a request id. A terminal
or backend without structured permission answers `needs you at its keyboard` and exposes no
Allow/Deny control. Queue detail names `concurrency ceiling` or `current turn` from the runtime's
own `queuedReason`; no consumer switches on a backend id.

## Acceptance

The pure table covers approval arrival/answer/exit, oldest pending request, both queue reasons,
stopped versus failed, a sealed run with no outcome, missing mapping, and terminal versus
structured approval. `a turn` is rendered as `turn complete`, never task success.

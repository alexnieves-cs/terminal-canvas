# M197 — D05, one Start work action and every door a route into it

The guide's [D05](../../product-development-guide-2026-09-08.md#d05--start-work-from-an-issue-or-intention),
first half. D05 is M197–M198: **M197 is the flow** (the guide's steps 1–4 and the reachable
half of 6) and **M198 is idempotency and partial-failure recovery** (step 5), which this spec
names by measurement and does not spend.

## 1. The problem, as four measured facts

The M113–M116 path — board record, lane, teammate, chat, PR — is built and works. What is
missing is the *start*: the point where a person with an intention and a repository has to
become a dispatched conversation. Four things are wrong with it, and each is silent.

### A. The `root` argument has no caller, so two of the three sources cannot start at all

`dispatchWorkItem(itemId, teammateId, root?)` (`Canvas.tsx:4281`) takes a chosen repository
root as its third argument. Every caller passes two:

| Door | Site | Passes `root`? |
|---|---|---|
| the Teammates-pane drop | `TeammatesPane.tsx:82` → `Canvas.tsx:6570` | no |
| the rail's drop wiring | `Canvas.tsx:6068` | no |
| the card's `Assign to…` menu | `WorkNode.tsx:161` | no |
| the agent's `dispatch` verb | `usePaletteActions.ts:470` | no |

`board-lane.ts:52-55` then reads `req.repo` (derived from the item's key) and `req.root`, and
when both are absent refuses:

> this item names no repository — choose which place `<name>` should work it in

**That sentence names a choice no surface offers.** And `repoOfKey` answers `null` for
anything that is not `owner/repo#N`, so:

- a **typed** item (`source: 'typed'`, no key) is undispatchable;
- a **Jira** item (`PROJ-12`) is undispatchable;
- a **GitHub** item is dispatchable only when `findRepoUnderPlaces` finds a clone of its
  `owner/repo` at a teammate's place or one of that place's immediate children.

The typed door D05 names in its first sentence — `New work item…`, M113's own row — mints a
card that can never become work. Nothing on screen says so until a teammate is chosen and the
refusal lands in the card's `note`.

### B. There is no flow, only four surfaces the user must already know the order of

Starting work today is: open the GitHub or Jira panel → `Add to board` → open the Board pane
(or find the minted card on the canvas) → `Assign to…` → and, if the teammate has no place
holding the clone, leave for the Teammates pane, add a place, come back, and press again. No
surface states what is still missing, and none returns to where the user was.

### C. The agent's door answers before the work has happened

`case 'dispatch'` (`usePaletteActions.ts:465-471`) binds the item and the teammate by key,
calls the **void-returning** `self.dispatchWorkItem(...)` and returns `{ kind: 'ran' }`. The
verb is `async` and everything that can refuse — the place gate, the missing clone, git,
`agent:create`, and M82's budget on the first send — refuses *after* that return, into the
record's `note`. An agent that dispatched into a refusal is told it ran. This is the same
class as M149's `historyWord` finding: a result computed and never read.

### D. The first send's answer is dropped

`await window.canvas.agentSession.send(chatId, ...)` (`Canvas.tsx:4315`) ignores its
`SendAnswer`. `send` has a `{ refused }` arm — M82's budget ceiling refuses and **stores
nothing**, by that milestone's own rule — so a dispatch over budget leaves a chat panel, a
worktree, a card marked `todo`, and no message anywhere, with no note. The card's own state
machine then never reaches `working`, because `working` is the runtime's word from a turn
that never started.

## 2. The policy

**One action. Ask only for what cannot be derived. Dispatch without a sheet when nothing is
missing.**

A start is a TRIPLE:

- a **task** — a work item, existing or minted here;
- a **repository** — an absolute root on disk that is a git worktree root;
- an **agent** — a teammate (the identity; the chat is its conversation and the session its
  execution — D01's distinction, unchanged).

Rules, each bound by a check:

1. **`startWorkNeeds` is pure and decides whether a sheet opens.** Given the subject and what
   the app knows, it answers the missing inputs in a fixed order — **`task`, `agent`, then
   `repository`, and that order is a dependency, not a preference**: the repositories on offer
   are the ones under the *chosen teammate's* places, so there is nothing to list until the
   agent is known. **Empty means dispatch immediately** — the Teammates-pane drop
   of a GitHub card onto a teammate whose place holds exactly one clone of it still starts
   work in one gesture, as it does today.
2. **The repository is main's fact, offered as a choice.** `board-repo.ts` already walks a
   teammate's places and their immediate children to find one clone; the same bounded walk
   answers *every* repository under those places. A new `board:repositories` invoke returns
   them, and the sheet's repository field is that list plus, when the item names an
   `owner/repo` that the list holds exactly once, an `auto` row that says which. The renderer
   never decides what is a repository — it renders main's answer.
3. **The choice is `root`, and `root` reaches `board:lane` unchanged.** No second executor:
   the sheet's submit calls the same `dispatchWorkItem`, which calls the same `board:lane`,
   which calls the same `ensureForPanel`. The dead third argument becomes live; nothing in
   main changes shape.
4. **Nothing is granted implicitly.** A teammate with no places is offered DISABLED with the
   fix (`teammateRefusal`, unchanged), and the sheet's agent field offers `Add a place…` as a
   named route to the Teammates pane — never a checkbox that widens `places[]` from here. The
   Places gate, the service grants and `insidePlace` are untouched; a repository offered in
   the list is one *already* inside a place, because the walk starts at the places.
5. **Three states everywhere the list is empty.** `no teammate has a place yet`, `<name>'s
   places hold no repository` and a real list are three renderings, not one.
6. **The task and the repository are stated before dispatch.** The sheet's summary line names
   both, in `display-path.ts`'s words for the root — the path rule, unchanged.
7. **The verb answers.** `dispatchWorkItem` returns a `StartWorkOutcome`, the agent's
   `dispatch` arm awaits it and refuses by the same sentence the card's note carries, and the
   first send's `{ refused }` arm becomes a note rather than silence.

## 3. What is NOT in M197

- **Idempotency and recovery (D05 step 5)** — M198. Measured and recorded here so the ledger
  can point at it: a second start mints a fresh `c<n>` chat id, and `ensureForPanel` reuses a
  record **by panel id and root**, so a retry after any failure past the lane step creates a
  second worktree and a second branch. The item's `worktreeId` is written only after
  `agent:create` succeeds, so the first lane is orphaned with nothing naming it.
- **A first-class project record.** D01's contract holds: project, workspace and task do not
  merge, and nothing here adds one to `LayoutSnapshot`.
- **Live provider writes.** No new GitHub or Jira write; the Jira transition owed since M24 is
  still owed.

## 4. The shape

### `src/shared/start-work.ts` (new, pure)

```
StartWorkSubject      = { kind: 'item'; itemId } | { kind: 'typed'; title } | { kind: 'provider'; ... }
StartWorkRepo         = { path: string; repo: string | null }
StartWorkNeed         = { field: 'task' | 'agent' | 'repository'; why: string }
startWorkNeeds(...)   → StartWorkNeed[]           // empty ⇒ dispatch without a sheet
resolveRepository(...)→ { kind: 'auto'; path; repo } | { kind: 'ambiguous' } | { kind: 'none' }
startWorkRefusal(...) → string | null              // the blocking sentences, one list
startWorkSummary(...) → string                     // the stated task · repository · agent
```

### `src/main/board-repo.ts` (extended)

`repositoriesUnderPlaces(places, deps)` — the same one-level walk, a new injected
`isRepoRoot`, capped at `REPO_LIST_MAX`, deduped by path, in place order, each entry carrying
its normalised origin or `null`.

### IPC

One new invoke, `board:repositories` (`BOARD_REPOSITORIES`), renderer → main, taking a
`teammateId`, answering `{ kind: 'repos'; repos } | { kind: 'refused'; reason }`. Both IPC
diagrams (this file's copy and `README.md`'s pinned one) gain the line; `verify:ipc`'s
`EXPECTED_CHANNELS` is re-derived.

### The sheet

`src/renderer/palette/start-work-sheet.ts` (pure field model) and `StartWorkSheet.tsx`
(render and focus only), the `SpawnSheet` split. It reuses the `.sheet__*` classes; no new
DOM alias is renamed.

### Doors

`Start work…` in the palette; the card's menu opens the sheet when anything is missing and
dispatches when nothing is; the Teammates-pane drop is the same action with the agent
pre-filled; the agent's `dispatch` verb keeps its spelling and gains the awaited answer.

## 6. Acceptance

A user starts an actual task without navigating several configuration areas: a typed
intention, a chosen repository and a teammate, in one place, ending on the conversation. A
start that cannot proceed says which of the three is missing and where to fix it, and mints
nothing.

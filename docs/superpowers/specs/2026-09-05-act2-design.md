# Act II — identity and scope (M100–M103)

**Status:** design, 2026-09-05. **Branch:** `m100-teammates` (one branch, one merge for the act).
**Kind:** runtime + surface. **Briefs built against:** 1.x principles 7 (three states), 9 (a
disabled row names the fix); 2.0 principle 13 (`Canvas.tsx` owns the gesture, the pure module
owns the rule); the credential boundary (`credential-store.ts`, the absent `credential:get`).
**Thesis sentence:** an agent is a persistent identity with a scope — a name, a brief, its own
memory, and explicit PLACES it may touch — not a spawned process; and the same three-way split
(folder, service, schedule) that keeps secrets in one process keeps an agent's reach visible.

## M0, recorded — the `<webview>` spike (decides M103)

Measured 2026-09-05 with a throwaway Electron script in the session scratchpad (a measurement,
not a check, the way M91's was). The built renderer's own `index.html` was loaded — the shipped
CSP `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self'
data:` — with `webviewTag: true` added to `webPreferences`, and a `<webview src="http://127.0.0.1:<port>/">`
appended inside a `transform`ed world div under an `overflow: hidden` host:

| Question | Answer |
|---|---|
| Loads without a `securitypolicyviolation`? | **Yes.** `did-finish-load` fired, the `securitypolicyviolation` listener recorded nothing, `getURL()` answered the page's URL. A `<webview>` is a guest process, not a frame; `frame-src` does not reach it. |
| Pans, zooms, clips, z-orders with the world? | **Yes.** At `translate(50,50) scale(1)`, `translate(100,60) scale(0.5)` and `translate(-100,-80) scale(1.6)` the element's rect AND the painted guest followed the transform (the guest's text scaled); at `translate(350,250)` it clipped at the host's edge; a sibling div with a higher z-index painted over it. |

So M103 exists and M104 gets a browser seat. The one decision to argue for is `webviewTag:
true`, which Electron's own docs discourage: the argument is that every property the docs warn
about is closed by a check in this act (no node integration in the guest, context isolation on,
a permission handler denying by default, `setWindowOpenHandler` refusing new windows, and
`will-attach-webview` stripping any `preload`/`nodeintegration` a page could set) — and that
the alternative shapes were measured and failed (M91). The renderer's CSP is NOT relaxed.

## M100 — Teammates, and Places

### The record (`shared/teammates.ts`, `shared/layout-schema.ts`)

`PersistedTeammate`: `id`, `name`, `brief` (the system prompt it carries), `places: string[]`
(absolute folders, the ONLY folders it may touch), `services: string[]` (M102), `skills:
string[]` (paths of `.md` skills it may read — a place rule applies), `memory: string` (the
slug of its own memory file), `chats: string[]` (panel ids), `messaging: boolean`,
`scheduling: boolean`. Saved top level as `teammates` beside `presets` and `templates`, with
the record rules: absent is every pre-existing file and warns nothing; a malformed record is
dropped BY NAME and the collection survives; an absent optional field stays absent through
every copy site (`carryTeammate`, the M92/M99 shape). `TEAMMATES_MAX` (50). A chat panel
record gains `teammateId?: string` (absent for every pre-existing chat).

### Places (`shared/places.ts`, `main/places.ts`) — the milestone

`insidePlace(candidate, places, realpath)`: a path is allowed iff its REAL, normalised form
(`..` collapsed, symlinks resolved through the injected `realpath`, a relative path refused
outright rather than resolved against any root) is equal to or under a place's real form. The
three traversal cases are the whole point and each is a check: `..` (`~/work/api/../../.ssh`),
a symlink inside a place pointing out (`~/work/api/link → /etc`), and a relative path
(`api/src` with no root — refused, never resolved against cwd or home). The check runs on the
NORMALISED path (M87's `%2e%2e` lesson).

**Checked in MAIN, before any spawn resolves a cwd and before any file verb answers**: the
`agent:create` and `spawn:sheet` handlers ask `placesGate(teammateId, cwd)` before
`resolveCwd`; `file:read`, `file:write`, `file:create` and `fs:list` ask it when the request
carries a `teammateId`; a plan's `type`/`send` into a teammate's chat is unaffected (the
teammate's cwd was gated at create). A path outside every place refuses BY NAME with the fix:
`~/.ssh is outside every place of <name> — add ~/work/api to this teammate's places`. A
teammate with NO places has no filesystem at all (a chat refuses to spawn until one is added),
never "everything".

**Why three separate permissions.** Folder, service and schedule fail differently: a wrong
folder leaks a file, a wrong service spends a credential, a wrong schedule runs unattended. A
single `trusted` flag hides which one the user granted; three lists say it.

### Memory per teammate

A teammate's memory is its own append-only JSONL under `userData/memory/teammates/<slug>.jsonl`
through the SAME store (`memory-store.ts` takes a dir; the teammate's file is a second
instance), BESIDE M83's per-repository memory — different axes: what the repository decided vs
what this identity learned. A teammate's chat carries BOTH bounds above its composer
(`MEMORY_CONTEXT_MAX` each, the M83 rule extended), so nothing is sent that was not shown.

### The surface

The navigator gains a **Teammates** pane (sixth): one row per teammate (name, `N places · N
services`, `messaging`/`scheduling` marks), `New teammate…` (the palette's text mode for the
name, then the sheet), and a detail with the brief, the places list (`add a place…` through the
OS folder dialog — a place is CHOSEN, never typed, so a typo cannot widen it), services (M102),
skills, memory (its rows, `tc memory add --teammate`), chats. The spawn sheet's `what` gains
`chat as <teammate>` rows from the record; a teammate's chat carries its brief as
`--append-system-prompt` on every spawn (the M81 supervisor rule) and its `teammateId`. The
rail row and the chrome name the teammate (`ada · api (chat)`).

### Failure modes, each with its check

| Failure | Check |
|---|---|
| `..`, a symlink out, a relative path | `verify:teammates places.1–.3` (fake fs / injected realpath) |
| A record dropped whole, or a field written `undefined` | `verify:layout teammate.1–.2` |
| A cwd outside every place resolving in main | `verify:teammates gate.1` (the gate refuses before `resolveCwd`) |
| A teammate with no places reading as unrestricted | `verify:teammates places.4` |
| Two memories collapsed into one | `verify:file memory.2` (two stores, two files, both bounds) |

## M101 — Routines

M0 confirmed the arming path is live: `watcher:create` in `main/index.ts` arms a real interval
and the renderer re-creates every watcher on restore. A routine is therefore ONE surface plus
one tick: `PersistedRoutine` (`id`, `name`, `teammateId`, `everyMs`, `prompt`, `paused`,
`lastRun?: { at, outcome, error? }`, `missed?: { at }`) saved top level; on each tick main
creates a FRESH chat for the teammate (`agent:create` through the ordinary path, the Places
gate included) and sends the prompt with a system prompt that says the design rule verbatim:
**routines gather, analyze, draft and prepare; irreversible actions stay behind confirmation.**
A routine may not carry a plan holding a destructive verb — refused at save time by name
against M96's table (`planIsDestructive`). It requires the teammate's `scheduling` permission
(refused by name otherwise). In-app only, said on the row (`runs while the app is open`); a
tick that would have fired while closed is recorded as `missed at <time>` on the row when the
app next starts (the schedule's `lastRun.at + everyMs < now`) — never skipped silently. `Run
now` / `Pause` / `Resume` / `Open last` (the last run's chat panel, or its error).

Checks: `verify:layout routine.1` (record rules), `verify:file routine.1` (the tick over the
fake runner: a fresh chat per tick, the missed mark, pause), `verify:verbs routine.1` (a
destructive plan refused at save).

## M102 — Service scope per teammate, and the spend-approval card

`docs/build-log/m87-broker.md`, `m88-github.md`, `m89-integrations.md` read first. Adds two
things; rebuilds nothing.

**Scoping.** `BrokerRequest` gains `teammateId?`; the broker's deps gain `services(teammateId)`
and refuse `code: 'not-granted'` with the fix (`grant github to <name> in the Teammates pane`)
BEFORE the credential is read — so the store's three readers stay exactly three
(`verify:meta readers.1` unchanged). The audit row carries `teammateId`. Credentials never
enter a prompt or a transcript: `verify:credentials scope.1` asserts the teammate's brief and a
chat's first message contain no token after a broker call, and the readers pin is re-asserted.

**The approval card.** A WRITE through the broker (method not in `READ_ONLY_METHODS = {GET,
HEAD, OPTIONS}` — data, not a heuristic on the path) raises a permission request on the
teammate's chat through M76's tracker (`permission-request` with tool `broker:<service>`,
input `{ method, path, account, cost }`), answered through the one `agentSession.answer` door
with `Allow for session` available under M98's never-persisted rule; the broker waits on the
answer (a grace, then refused `code: 'not-answered'`). Read-only calls run uninterrupted. The
card names service, connected account (`credential:list`'s label), action, target resource,
and the stated cost or credit use (`cost` on the request when the caller knows it; `unknown`
said as such).

**Constraint 1 stands.** A service is connected by pasting a token through the existing
Connect verb; OAuth is the missing half — a redirect listener on the control socket's port,
a PKCE exchange in main, the refresh token in the credential store under the same three
readers — and no suite here could reach a real provider.

## M103 — The browser pane

*Reverses `2026-09-03-v2-scope-decision.md` §5, narrowly.* The decline was right for a general
web panel and wrong for a verification surface docked beside the dev server that produced it:
on an infinite canvas the browser sits literally beside the panel that started the server, and
an `exit-ok` → reload handoff edge is the obvious wiring, which M78's table already supports.
`<webview>` is the one shape that threads both of M91's failures (above), and M0 measured it.

An eleventh panel kind, `browser` (`url`, `title?`): a `<webview>` in its own guest process,
`partition="persist:tc-browser"`. Address bar and controls are APP CHROME outside the guest.

**Four security properties, each a check:**
1. A hostile page cannot paint a false address: the bar reads `webview.getURL()` on every
   `did-navigate`/`did-navigate-in-page`, never `document.title` or anything the page posts;
   `verify:panels browser.1` serves a page that rewrites its own title and history and asserts
   the bar reads the real URL.
2. Reading the pane counts as leaving the app: `browser:read` (main, `executeJavaScript` of
   `document.body.innerText` capped) passes `outward`, and the plan/agent confirmation says
   `the content is a remote page's`; `verify:verbs gate.3`.
3. Only `http(s)` pages are readable: the scheme check is in MAIN on the read path
   (`browser:read` refuses `file:`, `data:`, `about:` by name), not on navigation alone;
   `verify:file browser.1`.
4. No node integration, context isolation on, a permission handler denying camera, mic,
   geolocation and notifications by default, `setWindowOpenHandler` refusing new windows, and
   `will-attach-webview` stripping `preload` and forcing `nodeIntegration=false`;
   `verify:meta browser.1` reads `main/index.ts` as text for all five.

`link:open` stays the door for a page that is not local. The pane's `Open in browser` is a
labelled verb.

**Declined by name: the iOS Simulator pane.** There is no seam for it in this repository, it is
a macOS screen-scrape (`xcrun simctl io screenshot` in a loop, or a window capture), and its
scope is unbounded (input forwarding, device selection, a second app's lifecycle). Declined.

## What the act must not break

The credential store's three readers; `usePaletteActions` as one `useMemo`; the M61 identity
rule; `registry.version()`'s contents; the renderer's CSP.

`teammate` (the Teammates pane with one teammate's places and a refused path), `routine` (a

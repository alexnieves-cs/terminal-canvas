# M188 — node schemas, a bounded executor, and Test this node

Act V of the v9 run (the plan's M189 and M190 rows, consolidated). The 5.0 brief: *"The
inspector renders fields from the kind's schema… Test this node reports input, output, duration
and a named failure without falsely running its neighbors."*

## The registry is one table

`shared/node-schema.ts` holds one entry per workflow node kind: its label, its sentence, its
fields (name, label, kind, required, placeholder, example) and whether it is EXECUTABLE. Three
consumers read that one table and nothing else — the library (M183), the inspector's editor
(M183) and the executor below — so a kind cannot look like one thing in the editor and behave
as another when it runs. M183's `fieldsOf` and `LIBRARY` are re-derived from it rather than
kept beside it.

## Two executable kinds, and why only two

- **`action`** — a canvas verb line, executed through the SAME `runAgentPlan` the agent door
  takes: the plan is built, refused by name if it cannot bind, and every destructive step still
  needs its confirmation. This is the kind that closes the four-door rule: every v9 verb's
  `V9_DOORS` row has named `WORKFLOW_EXECUTOR_DUE` as an owed workflow door since M180, and an
  `action` node running `note-add sticky` IS that door. `closure.v9.1` stops accepting an owed
  reason for a verb an action node can run and asserts the door instead.
- **`http`** — a GET through an injected fetcher, with the response capped and passed through
  `outward` (it is a remote page's content reaching this app, M96's gate). Any other method is
  REFUSED BY NAME with the reason: a write belongs on the broker's approval path (M102), which
  no node speaks to yet, and a node that could POST without an approval door would be a way
  around the one this app already built.

**Struck, with reasons.** A `shell` node duplicates the terminal node the graph already has,
with a second process seam and no approval story of its own. A `transform` node needs an
expression language this run cannot design and measure honestly in the time it has, and a
half-designed one becomes a compatibility burden the moment a template holds it. A Slack, email
or webhook node needs a workspace token, a sender domain, an armed listener or real elapsed
minutes to prove anything, and this run can prove none of them — they are recorded in the
ledger as struck rather than shipped untested.

## Test this node

`node:test` runs ONE node with an input the person supplies and answers with the input it used,
the output, the duration in milliseconds, and a NAMED failure. It runs the node and nothing
else: no neighbour is started and no run is recorded, which is what "without falsely running its
neighbors" means and what the check asserts by counting the panels and runs before and after.

## Doors

`node-test` ships as a verb, a palette row and a control in the inspector for a selected node.
The `action` kind is itself the workflow door for the verbs it can run.

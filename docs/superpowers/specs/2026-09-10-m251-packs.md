# M251 — packs: a discipline in one file, read before anything is added

A **pack** is a shareable bundle for one discipline: the workflows, saved prompts and object
presets someone assembled for a kind of work, plus the credentials and external tools that work
needs. It is the portable file's (M189) rules applied to *library* objects rather than to a canvas.

Phase A (this milestone) is the format and an import that is inert and shows its manifest first.
Phase B (a first integration pack) is sketched at the end and is **not built** until confirmed.

## The file

`shared/pack.ts`, pure, plain-node checked. A pack is its own envelope, `.tcpack`:

```
{ version: 1, kind: 'pack', createdAt, app,
  manifest: { name, version: "x.y.z", description?,
              contents:    [{ kind: 'workflow'|'prompt'|'preset', id, name }],
              credentials: [{ service, fields: [{ id, label }] }],
              tools:       [{ command, why? }] },
  templates: [...], prompts: [...], presets: [...],
  omitted: [{ what, why }], redacted: <count> }
```

- **Its own `kind`, never a portable kind.** Adding `pack` to `PORTABLE_KINDS` would let
  *Import canvas* accept a pack and make a workspace of it. Each door refuses the other's file
  by name ("that is a canvas file — use Import canvas").
- **Built field by field and scrubbed**, exactly as `buildPortable` is: every string passes
  `redactSecrets`, and the count rides on the record. So `shared/pack.ts` joins
  `verify:verbs gate.2`'s named caller list.
- **The manifest names credentials by service and FIELD, never by value.** There is no key on the
  record a value could occupy; the check asserts on keys, not on content.
- **What never travels is named in `omitted`:** routines (they would schedule themselves),
  skills (every agent reads a skill, so writing one is not inert — a pack may *declare* a tool it
  needs, never install one), and credentials.

## Parsing: absent, malformed, unknown

`parsePack(text)` has three top-level answers — `not-a-pack` (with a named reason: not JSON, a
canvas file, no name, no version), `unknown-version`, and `pack` with warnings. Inside the
manifest the repo's rule holds per key:

- an **absent** optional key (`description`, `credentials`, `tools`, a tool's `why`) warns nothing
  and stays absent — never written back as `key: undefined`;
- a **present-but-malformed** value warns by the key's name and is dropped, never coerced
  (`version: 3` is not `"3.0.0"`);
- an **unknown** entry — a content kind this app has no shape for, a credential service not in
  `SERVICES` — costs that entry, named, never the collection.

The contents list is reconciled against the payload. A listed item with nothing behind it, and
a payload item the list does not name, are both warnings. The manifest is the thing a person
reads before agreeing, so it must not under-state what will be added.

## Requirements: named per field

`packRequirements(manifest, credentialMetas, tools)` answers with one row per credential
**field**:

| state | when | sentence |
|---|---|---|
| `connected` | a meta for the service, no `rejectedAt` | — |
| `rejected` | `rejectedAt` present | *GitHub · personal access token — the stored token was rejected; replace it in ⌘K › Credentials* |
| `not-connected` | no meta | *GitHub · personal access token — `notConnectedReason('GitHub')`* |
| `unknown-service` | service not in `SERVICES` | *this app cannot hold a "x" credential yet — "API key" cannot be connected* |

Main computes this from `credentialStore.list()` — metadata only. No plaintext is read, so the
store's pinned reader list (`readers.1`) does not grow. Tools are `found`, `missing` or
`unanswered`: a probe that could not run is not a tool that is absent. Unmet requirements
**explain**. They never block the add, because nothing a pack adds runs anyway.

## The import is inert and previews first

1. `pack:read` opens the system file chooser, parses, and computes requirements. **It adds
   nothing.**
2. A preview sheet shows the name, version, description, contents grouped by kind, a row for
   each requirement, the file's warnings and what it left out. The primary action reads
   *Add N objects*; Cancel leaves the store byte-identical.
3. On *Add*: fresh ids for every item. Workflows are saved `reviewed: false` (M189's rule), and
   presets are saved with a new `reviewed: false`. Prompts are inert text and are saved as they are.
4. **An unreviewed preset is refused at spawn, by name, in main.** A preset carries a command,
   so an imported one would otherwise be a stranger's process one click away.
5. **Mark as read.** A workflow's inspector and a preset's row get an *I've read this* control
   that clears the flag. Without it, M189's refusal is permanent: nothing in the app cleared
   `reviewed` before this milestone.

## Doors

`pack.import` and `pack.export` palette rows. The verbs are `import-pack` and `export-pack`, and
`export-pack` is destructive because a named path skips the save dialog, the same reasoning as
`export-canvas`. Both are refused at the agent door, as the portable verbs are. Each verb's
canvas door is owed by name in `V9_DOORS` (M252), because a pack is the library, not something
on this canvas.

**Decisions made while building, recorded here so they are not re-litigated:**

- **Main builds the export from its own store.** The renderer's preset rows carry no args, env
  or options, so a pack the renderer assembled would be a lossy copy. Phase A exports the whole
  user library — workflows, saved prompts and presets — named after the active workspace.
  `tools` is derived from the presets' command words. Picking individual items is a later
  refinement; the import preview is where the reader sees exactly what the pack holds.
- **Main does the adding.** `pack:read` holds the parse under a token, and `pack:add` takes only
  that token. The renderer can confirm only what it was shown, and main mints every id against
  its own store.
- **"I've read this" is a palette row.**
  - An unread preset's spawn row is disabled with `REASON_UNREAD_PRESET`, and a
    `preset.read.<id>` row sits beside it, whose subtitle is the command and directory.
  - An unread workflow gets a `workflow.read.<id>` row, whose subtitle is its action lines.
  - Neither statement has a verb: both are in `EXCLUDED_ACTIONS`, because a plan that could
    make them would undo the gate.
  - An inspector control is a later refinement.
- **One handler factory.** `main/pack-handlers.ts` is built by production and by the panels
  harness. Only the choosers differ between them, so the end-to-end check drives production code.
- **An unknown credential service is kept, not dropped**, as the requirements table says: a
  dropped requirement would read as a pack that needs nothing.

## What this does not do

- It installs no skill, and no MCP server or plugin.
- It stores no credential. A pack can only say which ones it needs.
- There is no registry and no download. A pack is a file a person was given.

## Phase B sketch (not built until confirmed) — a dev-relations pack

The first integration pack targets **dev relations**: release notes, changelog drafts and
announcement workflows. It reuses the existing `github` credential, so it needs no new
`SERVICES` entry and no new plaintext reader. Every write goes through the broker, whose
non-GET methods already raise a per-request spend card. Every body passes `outward()` before it
leaves. A plan cannot reach a write, because `verb-table.ts` already keeps `openPr`/`commentPr`
out of plans for the reason that a plan has no teammate to answer the card. A future
social-posting service would be a new `SERVICES` entry and a broker table row, and its spec
would need its own decisions.

# M255 — packs, Phase B: the dev-relations pack, and no GitHub write without a person

The first integration pack. The user chose all four dev-relations actions: release notes,
changelog entries, PR comments and announcement drafts. Announcements live on GitHub itself
(a release body or a GitHub Discussion). The pack ships as a sample `.tcpack`.

## What was wrong first

The broker asked a person before a write **only when the caller was a chat bound to a teammate**
(`broker.ts`, M102). A terminal, a workflow's chat node (template chat nodes carry no teammate)
or `tc api` outside a panel could POST to GitHub with no card. One "Allow for session" on a
`github` card approved every later write from that chat. No request body passed `outward()`.
A pack whose agents are told to "publish" would have made all three reachable in one line. The
user chose to close the gap here.

## Rule 1 — the broker writes only for a person

- A non-read-only request needs **a teammate's per-request card** or **`personConfirmed: true`**.
- `personConfirmed` is set only by main-side code that has just shown its own confirmation.
  `tc api`'s control handler builds its broker request field by field and never forwards it.
- A write with neither is refused as `not-asked` **before the credential is read**.
- Board PR actions always carry a teammate, so they keep working.
- A broker card's tool name is unique per request, so a session grant can never answer a later
  write.

## Rule 2 — publishing is a person's act, with the text in front of them

`main/github-publish.ts` does three things: publish a release, comment on a PR, post a
Discussion. Each takes a **draft file** and follows the same steps:
1. Resolve the repository from the file's own `origin` remote.
2. Title it from the first `# heading`, or the file name.
3. Pass the body through `outward()`.
4. Show the person the repository, the target, the title, the opening lines and the redaction
   count in a confirmation that defaults to Cancel. It asks every time.
5. Only then call the broker with `personConfirmed`.

A Discussion's GraphQL lookups run only after the confirmation, so a cancel costs nothing. An
unknown category is refused by name, and no mutation is sent.

Results come in three kinds:
- `published`, with the URL;
- `cancelled`;
- refused, one of `no-credential` / `refused` / `unavailable`, each with a sentence.

The doors:
- The verbs `publish-release <tag> <file>`, `comment-pr <number> <file>` and
  `post-discussion <category> <file>`. All are destructive, and all are refused to a teammate's
  plan.
- Palette rows on a focused file panel, which ask for the tag, number or category.
- The workflow door is owed by name: an action node cannot answer a confirmation.

## The pack

`shared/devrel-pack.ts` builds the pack with `buildPack`. It is the one source for
`docs/packs/dev-relations.tcpack` and for the copy "Import the sample dev-relations pack…"
writes under `userData/packs`.

- **Four workflows.** Each has a chat node that drafts into a file, beside read-only terminals:
  release notes, a changelog entry, a release announcement, a PR comment. Every chat message
  ends with a sentence that makes it draft-only.
- **Four prompts:** the release-notes voice, the changelog format, the announcement format, and
  the PR-comment tone.
- **Two read-only presets:** merged PRs, and commits since the last tag.
- **Requirements:** the `github` credential's personal access token, and the `gh` and `git`
  tools.

No preset or terminal node carries a write command (a check forbids them), because a `gh` write
uses gh's own login and would bypass rules 1 and 2.

## Owed by hand

- One real release, one PR comment and one Discussion against a scratch repository.

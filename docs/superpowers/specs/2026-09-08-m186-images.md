# M186 — durable images: drop, paste, capture, and an identity that travels

Act IV.1 of the v9 run (the plan's M187 row). The 5.0 brief's "Preview and media" paragraph is
the standard: *"Images preserve aspect ratio and show real pixels; missing bytes leave an object
with a Replace action"*, and its "Sharing and extensions" paragraph requires an asset identity an
export can carry.

## What exists

M181 gave the canvas an image kind that holds an ABSOLUTE PATH and nothing else, and a
main-side read that decides the media type by magic number with four arms. M185 writes captures
under `userData/captures`. Nothing brings a picture in from outside the app, and nothing gives a
picture an identity that survives being moved to another machine.

## What ships

**One store, content-addressed.** `main/asset-store.ts` copies bytes into
`userData/assets/<sha256>.<ext>` and answers with the id. The address is the CONTENT, so the
same picture dropped twice is one file and the second write is skipped — and an id is a fact
about bytes rather than about a filesystem, which is what lets M190's export carry it. Two caps,
each REPORTED and never silent: a single asset over `ASSET_MAX_BYTES` (10 MB) is refused by name
with its size and the cap; a store over `ASSET_STORE_MAX_BYTES` (200 MB) is pruned oldest-first
by mtime, and the prune is counted on the result. The bytes are checked by MAGIC NUMBER before
anything is written — `imageMediaType`, M181's own function, so the store and the reader cannot
disagree about what an image is.

**A picture arrives three ways and lands the same way.** A drop of an image file on the canvas,
a paste of a clipboard image with no terminal or chat to take it, and M185's capture all put
bytes in the store and mint one image panel at the point of the gesture. The existing agent
targets keep their behaviour exactly: a drop on a chat is still an attachment (M75) and a paste
into a terminal is still M145's shell-quoted path — the canvas is the arm for a gesture that
landed on NOTHING, which is the arm that did not exist.

**A picture's identity travels.** The image record gains `asset?: string` beside its `path`:
absent on every pre-M186 record and on any picture the person pointed at in place, present when
the bytes are in this app's store. The path is where the bytes are on THIS machine; the asset id
is what they ARE. Malformed costs the field, never the panel.

**Missing bytes leave an object with a Replace action.** The node's `missing`, `too-large` and
`not-an-image` arms each keep the panel, name the fix, and offer Replace, which opens the
system's own file chooser in main and puts the chosen file through the same store. A picture
whose file was deleted is a picture the person can repair, not a hole.

## Doors

`image-add` (a path) and `image-replace` (a panel and a path) ship as verbs, palette rows and
canvas gestures (drop, paste, and the node's own Replace). The workflow door is the recorded
omission every v9 verb carries until M188's executor.

## What this does not do

The store is not a garbage collector: pruning is by age against a cap, and a pruned asset's
panel shows `missing` with Replace, which is the same three-state answer a deleted file gets.
Nothing here sends an image anywhere — outward inclusion of pixels is M190's explicit human
review, and this milestone deliberately writes no export path.

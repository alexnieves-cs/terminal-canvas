# M23a — Shell information architecture: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the fixed four-column shell with an adaptive dock, one
navigator pane at a time, and a context pane split by question — reclaiming
412px of canvas at 1440px width and creating room for the ten backlog entries
that currently have nowhere to go.

**Architecture:** Three phases. **Phase 0** adds the mechanisms with no visual
change: an `'enum'` type on `SettingDef`, `verify:styles` 11 widened to iterate
theme blocks, and container-query scaffolding on `.shell` that reproduces
today's widths exactly. **Phase 1** replaces the tree/rail/inspector grid with
`dock | navigator | canvas | context` and drives residency from container
queries. **Phase 2** restructures the context pane into a pinned identity
header, three tabs, and a pinned action bar. Every pure model lands in the
plain-node `verify:rail` bundle before any component consumes it.

**Tech Stack:** TypeScript, React 18 (no StrictMode — see Global Constraint 6),
Electron, plain CSS with the M10 token system, esbuild-bundled plain-node
verify suites.

**Spec:** [`docs/superpowers/specs/2026-08-30-m23-interface-architecture-design.md`](../specs/2026-08-30-m23-interface-architecture-design.md)

**Not in this plan:** Phases 3 (panel chrome + semantic zoom), 4 (first run),
and 5 (light mode) get their own plans — `M23b`, `M23c`, `M23d` — matching how
`m8a`–`m8d` and `m9a`–`m9c` were sequenced. Phase 0's `'enum'` work is here
rather than in M23d because Phase 1 needs it for `shell.navigatorPane`.

## Global Constraints

Copied verbatim from the spec and from `CLAUDE.md`. **Every task's requirements
implicitly include this section.** Each fails silently when broken, which is
why they are constraints rather than preferences.

1. **Never measure the window.** Adaptation is a **container query on
   `.shell`**. No `window.innerWidth`, no `ResizeObserver` on the window. A
   window measurement makes edge pips aim at the window edge while the canvas
   ends 308px earlier, and every world point the HUD reports is wrong. Nothing
   throws. (Spec §7.1.)

2. **A resident region is a grid column, never an overlay.** Only the Compact
   breakpoint's **transient** drawers overlay the canvas, and they are
   dismissed on outside click and `Escape` exactly as the palette is. A
   resident overlay puts panels permanently under chrome and makes every
   `getBoundingClientRect()` in the canvas a lie. (Spec §7.2.)

3. **No chrome takes DOM focus.** Every control mounts `shellControl()` from
   `src/renderer/shell/shell-control.ts`, whose `onMouseDown: preventDefault`
   is the whole mechanism. The button works and the next keystroke goes
   nowhere otherwise. (Spec §7.3.)

4. **Nothing in this plan may spawn a process.** Navigating is
   `paletteActions.goToPanel` (frame, select, raise) and never
   `onSelectPanel`, which clears dormancy and calls `registry.wake`. (Spec
   §7.4.)

5. **Every row array a pane takes stays frozen on a signature.** `Canvas`
   re-renders on every mousemove and every frame of a drag; an unfrozen array
   defeats the memo outright and the symptom is invisible on a four-panel
   canvas. Signatures use `JSON.stringify`, never a separator join. (Spec §7.5.)

6. **React state updaters must stay pure.** No IPC call, no `void
   window.canvas.*`, inside a `setState` updater. `main.tsx` omits
   `StrictMode`, so the updater form is not broken today — it is one
   `<StrictMode>` away from writing every toggle twice.

7. **Structure on bare `:root`, colour only in `[data-theme]` blocks.**
   `verify:styles` 7 and 8 police both directions. A length in a theme block
   is a length every future theme has to repeat.

8. **Zero literals for space, radius, type and colour.** `verify:styles` 1 and
   4–6 assert this. Use `--sp-*`, `--r-*`, `--t-*` and the colour tokens.
   `--sp-8`/`--sp-9` and `--r-xl`/`--r-2xl` are for **floating surfaces only**
   — never on a `.rail-*`, `.dock-*` or `.inspector__*` row.

9. **`npm run verify` must be green before any task is claimed done**, and it
   must be run with `TC_VERIFY_SUFFIX` set so concurrent runs do not
   `kill-server` each other's tmux sockets. Use:
   `TC_VERIFY_SUFFIX=m23wt npm run verify`.

10. **Never hardcode a verify check number.** Derive the next free number by
    reading the target file's own last `ok(` call. This repo has renumbered
    check blocks at merge four separate times; a number written from memory
    collides silently and prints two different `133`s in one log.

### Task 1: `'string'` on `SettingDef`, with validation on both doors

`appearance.theme` (M23d) and `shell.navigatorPane` (Task 6) both need a
setting whose value is one of a fixed set of strings. `SettingDef['type']` is
`'boolean' | 'number'` today. `CLAUDE.md` records that an earlier draft added
`'enum'` and it was **removed** "rather than given a type-mapping layer, since
a customer-free abstraction is exactly what `ideas-backlog.md` #11 warns
against." That objection expires here: this task adds the type and the first
consumer arrives in Task 6.

**Both doors need it.** `setPreference` is the write path; `parsePreferences`
is the load path, and a hand-edited `layout.json` bypasses the write path
entirely. This is exactly the split `agent.idleAfterMs`'s bounds already have
(`verify:layout` 78/79 on the write path, 80b on the load path), and shipping
only one leaves the other as an unguarded door.

> **Naming, decided here so later tasks do not re-litigate it:** the type is
> spelled **`'string'`**, not `'enum'`. `SettingDef['type']`'s own comment says
> it "Tracks what `typeof` can actually answer" — `typeof 'light'` is
> `'string'`, and `'enum'` would break that stated invariant for the first
> time. The `values` array is what makes it an enumeration.

**Files:**
- Modify: `src/shared/settings-schema.ts`
- Modify: `src/shared/layout-schema.ts` (`parsePreferences`)
- Modify: `src/main/layout-store.ts` (`setPreference`)
- Test: `scripts/verify-layout.cjs`

**Interfaces:**
- Consumes: nothing.
- Produces:
  - `SettingDef['type']` widens to `'boolean' | 'number' | 'string'`
  - `SettingDef.values?: readonly string[]`
  - `export const APPEARANCE_CATEGORY = 'Appearance'`
  - `parsePreferences` and `setPreference` both reject a `'string'` value
    outside `values`, with a warning, exactly as they reject an out-of-range
    number

- [ ] **Step 1: Write the failing checks**

Append to `scripts/verify-layout.cjs`. **Derive `N` by reading the file's own
last `ok(` call and adding one** (Global Constraint 10) — do not hardcode it.

```js

// the preferences map refuse anything outside them. Two doors and therefore
// two checks: setPreference is the write path, parsePreferences is the load
// path a hand-edited layout.json takes — the same split agent.idleAfterMs's
// bounds already have (78/79 write, 80b load).
{
  const dir = mkdtempSync(join(tmpdir(), 'tc layout '))
  const file = join(dir, 'layout.json')
  const store = new LayoutStore({ filePath: file, schedule: (fn) => fn() })

  const good = store.setPreference('appearance.theme', 'light')
  ok(N, good === true && store.preference('appearance.theme') === 'light',
    `set=${good} read=${store.preference('appearance.theme')}`)

  // A value outside `values` is REFUSED and nothing is written. The second
  // clause is the whole check: asserting only the refusal passes against an
  // implementation that refused the caller and wrote the value anyway.
  const bad = store.setPreference('appearance.theme', 'chartreuse')
  ok(N + 1, bad === false && store.preference('appearance.theme') === 'light',
    `refused=${!bad} still=${store.preference('appearance.theme')}`)
}

// The load path: a hand-edited value outside `values` is DROPPED with a
// warning rather than carried into the map or coerced to the default. Its
// neighbour surviving is the half that proves "alone".
{
  const res = parseLayout({
    version: 1,
    workspaces: [{ id: 'w1', name: 'Main', panels: [], camera: { x: 0, y: 0, scale: 1 } }],
    activeWorkspaceId: 'w1',
    preferences: { 'appearance.theme': 'chartreuse', 'shell.railOpen': false }
  })
  const prefs = res.state.preferences
  ok(N + 2,
    prefs['appearance.theme'] === undefined
      && prefs['shell.railOpen'] === false
      && res.warnings.some((w) => w.includes('appearance.theme')),
    `theme=${prefs['appearance.theme']} rail=${prefs['shell.railOpen']} warned=${res.warnings.length}`)
}
```

non-speculative:


### Task 2: `verify:styles` 11 iterates theme blocks

Check 11 is the only check in the stylesheet suite that **computes** rather
than greps — it recovers every `--fg*` and `--s-*` hex and measures real WCAG
contrast for every text token against every surface it can land on. It assumes
**one** theme block. M23d adds a second, and a check that measured only the
first would report the light theme's contrast as the dark theme's: green, and
about the wrong palette.

Doing it in the phase with no visual change is deliberate. This is a change to
a *measuring instrument*, and changing an instrument in the same commit as the
thing it measures is how a bad measurement ships.

**Files:**
- Modify: `scripts/verify-styles.cjs` — check 11 only

**Interfaces:**
- Consumes: nothing.
- Produces: check 11 reports per theme (`1 theme(s) measured`) and fails naming
  the theme, so M23d's failure points at the right block.

- [ ] **Step 1: Add a temporary probe theme so the widening can be watched failing**

Append to `src/renderer/styles.css`:

```css

   OBSERVED failing on a second block rather than assumed to work on one. */
:root[data-theme="probe"] {
  --s-0: #ffffff;
  --s-4: #f0f0f0;
  --fg:   #eeeeee;   /* ~1.1:1 on --s-4 — must fail */
  --fg-2: #eeeeee;
  --fg-3: #eeeeee;
  --fg-4: #eeeeee;
}
```

- [ ] **Step 2: Run and observe it does NOT fail — this is the RED, inverted**

Run: `node scripts/verify-styles.cjs`

Expected: **PASS, all checks green.** That is the defect: the probe block's
unreadable pairs are invisible because the check only ever looked at the first
block. Record this result explicitly before continuing.

- [ ] **Step 3: Implement**

Rewrite check 11 to find **every** `:root[data-theme="…"]` block and measure
each on its own tokens:

```js
// Every theme block, measured on its OWN tokens. A single-block reading was
// correct while one theme existed and becomes silently wrong the moment a
// second lands: it would report the light theme's contrast as the dark
// theme's — green, and about the wrong palette.
const themeBlocks = [...css.matchAll(/:root\[data-theme="([a-z]+)"\][^{]*\{([^}]*)\}/g)]
  .map(([, name, body]) => ({ name, body }))

const failures = []
for (const { name, body } of themeBlocks) {
  const fg = tokensMatching(body, /^--fg/)
  // --s-5 is deliberately excluded: it is a PRESSED state, transient, and no
  // text is ever read against it. That exclusion is inherited from the check
  // as it stands; do not widen it here.
  const surfaces = tokensMatching(body, /^--s-[0-4]$/)
  for (const [fgName, fgHex] of Object.entries(fg)) {
    for (const [sName, sHex] of Object.entries(surfaces)) {
      const ratio = contrast(fgHex, sHex)
      const floor = fgName === '--fg-4' ? 3.0 : 4.5
      if (ratio < floor) {
        failures.push(`${name}: ${fgName} on ${sName} = ${ratio.toFixed(2)} < ${floor}`)
      }
    }
  }
}

ok(11, 'every theme block clears its contrast floor',
   failures.length === 0 && themeBlocks.length > 0,
   failures.length ? failures.join('; ') : `${themeBlocks.length} theme(s) measured`)
```

The `themeBlocks.length > 0` clause is the **non-vacuity guard** and is not
optional: a regex that matched nothing would report zero failures and pass,
which is a check that has quietly stopped existing.

- [ ] **Step 4: Run to verify it now fails on the probe**

Run: `node scripts/verify-styles.cjs`

Expected: **FAIL 11**, naming `probe:` pairs — and **not** naming `dark:`. The
dark theme must still pass, or the widening broke the measurement rather than
extending it.

- [ ] **Step 5: Delete the probe block and confirm green**

Remove the `:root[data-theme="probe"]` block, then run:
`node scripts/verify-styles.cjs`

Expected: **PASS 11**, detail reading `1 theme(s) measured`.

**Interfaces:**

- Produces: `.shell` as a named container `shell`, and three non-overlapping

  `1100–1599px` standard, `>= 1600px` wide.

- [ ] **Step 1: Record the current widths, to have a baseline to reproduce**

Run: `grep -n 'shell-tree-w\|shell-rail-w\|shell-inspector-w' src/renderer/styles.css`

- [ ] **Step 2: Implement**

In `.shell`, add the container declaration:

```css
  /* M23a. The query container for every breakpoint below. inline-size, never
     `size`: `size` containment requires a block size independent of contents,
     which height:100% does not guarantee, and a container that fails that
     condition silently stops matching — the queries would never fire and every
     region would sit at its fallback width forever, with nothing thrown.

     A CONTAINER query and never a media query, and that is Global Constraint 1
     rather than a style preference: a media query measures the viewport, i.e.
     the window, and the entire reason insetting the canvas is safe is that
     nothing in the renderer measures the window — useViewport, Canvas and
     EdgeIndicators all measure the .canvas host at event time. @container
     measures .shell, which is the element that actually owns this grid. */
  container: shell / inline-size;
```

Then, after the `.shell--*-collapsed` rules:

```css
/* M23a. The three breakpoints. All three currently produce today's widths
   byte-for-byte; Phase 1 changes what they contain. Declared now, in a task
   with no visual diff, so a regression in the MECHANISM is unambiguous and
   cannot be confused with a regression in the layout it will later carry.

   The bounds do not overlap and leave no gap: max-width 1099 and min-width
   1100 are adjacent integers. An overlapping pair would let both blocks apply
   at exactly 1100px and the winner would be source order, which is right until
   somebody reorders the file. */
@container shell (max-width: 1099px) {
  .shell { --shell-tree-w: 220px; --shell-rail-w: 240px; --shell-inspector-w: 260px; }
}
@container shell (min-width: 1100px) and (max-width: 1599px) {
  .shell { --shell-tree-w: 220px; --shell-rail-w: 240px; --shell-inspector-w: 260px; }
}
@container shell (min-width: 1600px) {
  .shell { --shell-tree-w: 220px; --shell-rail-w: 240px; --shell-inspector-w: 260px; }
}
```

# Phase 1 — Dock and navigator

**Phase exit criteria** (spec §10, Phase 1):

1. At a `.shell` inline-size of 1440, `.canvas` measures **1132px ± 1**.
2. A panel under the reclaimed width is still **promoted**.
3. Switching navigator panes spawns **nothing**.
4. A Compact drawer is dismissed by outside click **and** `Escape`, and a wheel
   over it moves no camera.
5. Every dock and pane control passes the **real-`sendInputEvent`** focus check.

**Risk: highest of the three phases.** Every check in `verify:panels` that
asserts an inset or a promotion is in scope.

### Task 4: `nav-dock.ts` — the pure model

The dock's entries, their badges, and which pane is active, as a pure function
over plain data. It lands in the plain-node `verify:rail` bundle before any
component consumes it, which is the precedent every view model since M8c has
followed: `inspector-fields.ts`, `rail-sections.ts`, `review-node-model.ts`,
`file-tree-model.ts` and `toolbox-node-model.ts` are all there for the same
reason — a pure function over plain data is checkable in milliseconds, and the
same logic inside a component is checkable only from the Electron tier.

**Files:**
- Create: `src/renderer/shell/nav-dock.ts`
- Modify: `scripts/rail-entry.cjs`
- Test: `scripts/verify-rail.cjs`

**Interfaces:**
- Consumes: `RailAttention[]` from `rail-sections.ts`; `RailRow[]` from
  `rail-rows.ts`.
- Produces:

```ts
export type NavPaneId = 'workspaces' | 'panels' | 'files' | 'attention'

export interface DockEntry {
  id: NavPaneId
  label: string
  /** One or two characters. Rendered as text, never an icon font. */
  glyph: string
```

```ts
/**
 * The dock's pure model: which entries exist, which is active, and what each
 * one's badge says.
 *
 * Pure by construction — no React, no DOM, and every import a type import — so
 * it joins the plain-node verify:rail bundle beside inspector-fields.ts,
 * rail-sections.ts and the three node models. That is the precedent every view
 * model since M8c has followed, and the reason is cost: a pure function over
 * plain data is checkable in milliseconds, and the same logic inside a
 * component is checkable only from the Electron tier.
 */

export type NavPaneId = 'workspaces' | 'panels' | 'files' | 'attention'

export interface DockEntry {
  id: NavPaneId
  label: string
  /** One or two characters, rendered as TEXT. Never an icon font: a font that
   *  fails to load leaves an app whose entire navigation is invisible, and
   *  --font-display's own comment records that a silently-wrong fallback "is
   *  exactly the kind of failure that ships". */
  glyph: string
  /** Undefined means NO badge. Never 0 — see the check that pins this. */
  badge?: number
  active: boolean
}

/**
 * The render order, exported so a check can assert it without restating it.
 * verify:palette 30 was rewritten for exactly this reason: an order written
 * down in two places is an order that drifts, and the copy nobody is looking
 * at is the one that goes stale.
 */
export const DOCK_ORDER: readonly NavPaneId[] = ['workspaces', 'panels', 'files', 'attention']

const LABEL: Record<NavPaneId, string> = {
  workspaces: 'Workspaces',
  panels: 'Panels',
  files: 'Files',
  attention: 'Attention'
}

const GLYPH: Record<NavPaneId, string> = {
  workspaces: '⌸',  // ⌸
  panels: '▤',      // ▤
  files: '⌷',       // ⌷
  attention: '⚑'    // ⚑
}

export function buildDock (
  activePane: NavPaneId | null,
  counts: { panels: number; workspaces: number; attention: number }
): DockEntry[] {
  return DOCK_ORDER.map((id) => {
    // Only Attention carries a badge, and only when non-zero. It is the one
    // fact that must stay visible when its pane is closed — losing the resident
    // Attention list is this milestone's one real trade (spec §3.3), and the
    // badge is the half of it that must not also be lost.
    const n = id === 'attention' ? counts.attention : 0
    const entry: DockEntry = {
      id,
      label: LABEL[id],
      glyph: GLYPH[id],
      active: activePane === id
    }
    // Assigned CONDITIONALLY rather than as `badge: n || undefined`, so the
    // key is genuinely absent rather than present-and-undefined. The same
    // absent-stays-absent rule `command`, `title` and `agent` already obey in
    // the layout schema, and for the same reason: `'badge' in entry` must read
    // false for an entry that has none.
    if (n > 0) entry.badge = n
    return entry
  })
}
```

```js
// in one check, because they are the two exits a transient surface owes — the

// one of them is a surface the user can get stuck behind.
// The outside click is a REAL sendInputEvent, not a dispatched MouseEvent: a
// synthetic event is isTrusted:false and Blink runs no default action for one,

// drawer's own list scrolls natively. Check 47's pair on a third surface, and

    before.grid !== null && JSON.stringify(after.grid) === JSON.stringify(before.grid),
```
